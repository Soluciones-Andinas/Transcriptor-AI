# ADR-018: Desactivación de DNS rebinding protection en MCP transport

## Estado

Aceptada

Fecha: 2026-05-11

## Contexto

FastMCP (SDK Anthropic `mcp[server]>=1.5,<2.0`) habilita por default una capa de DNS rebinding protection en el transport Streamable HTTP. La protección revisa el header `Host` de cada request entrante y rechaza con `421 Misdirected Request` si el valor no está en una allowlist (defaults: `127.0.0.1:*`, `localhost:*`, `[::1]:*`).

El propósito de esta protección es mitigar ataques de DNS rebinding contra MCP servers expuestos en `localhost`: un script malicioso en una web visitada por el operador resuelve un dominio controlado a `127.0.0.1`, el browser envía requests al MCP server con `Host: attacker.com`, la allowlist los rechaza.

Para el deployment de `transcription-api` esta protección causa fallas inmediatas:

- El rig está en una **intranet privada** (Soluciones Andinas + ZeroTier `10.147.17.0/24`).
- Los clientes (Claude Desktop / Claude Code) conectan vía la IP privada del rig: `10.147.17.142:8000` (vía ZeroTier) o `192.168.x.x` (LAN Sandinas).
- El header `Host` que llega es `10.147.17.142:8000`, **no** `127.0.0.1` ni `localhost`.
- Resultado: el SDK rechaza el request con `421` antes de invocar al `BearerAuthMiddleware`. El feature MCP no funciona desde clientes remotos.

Tres modelos de amenaza considerados:

1. **DNS rebinding desde web visitada por el operador**: requiere que el operador (a) ejecute un browser en la misma máquina/red que el MCP server y (b) visite una página maliciosa. En nuestro deployment el server vive en el rig sin browser; los operadores acceden por ZeroTier desde sus laptops. El vector no aplica directamente.
2. **Cliente legítimo con bearer comprometido**: cubierto por el `BearerAuthMiddleware`. Bearer hash con `hmac.compare_digest`, revocación manual vía `/auth/regenerate-mcp-token`.
3. **Atacante con acceso a la intranet**: ya tiene mejores vectores (Postgres en `5432`, MCP server en `8000`, scan de la red privada). El Host check no agrega protección efectiva en este modelo.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Mantener default (DNS rebinding ON) | Allowlist solo `127.0.0.1`/`localhost` | Más conservador; cumple defaults SDK | **Bloquea todo el deployment**: clientes ZeroTier reciben 421 |
| B: Allowlist extendida | Pasar `allowed_hosts=["127.0.0.1:*", "localhost:*", "10.147.17.0/24:*", "192.168.0.0/16:*"]` | Mantiene la protección | Requiere mantener la lista por cada CIDR de cada deploy; frágil cuando ZeroTier rota IPs |
| **C: Desactivar protección, confiar en bearer + red privada** | `enable_dns_rebinding_protection=False` | Simple, funciona out-of-the-box en intranet | Pierde defense-in-depth contra DNS rebinding desde browser local |

## Decisión

Se elige **Opción C**.

**Configuración as-built** (`src/transcription_api/mcp/server.py`):

```python
from mcp.server.transport_security import TransportSecuritySettings

_TRANSPORT_SECURITY = TransportSecuritySettings(
    enable_dns_rebinding_protection=False,
)

mcp_server: FastMCP = FastMCP(
    name="transcription-api",
    transport_security=_TRANSPORT_SECURITY,
    streamable_http_path="/",
)
```

**Justificación** anclada en la prioridad del proyecto (`<ARCH>` §0: `Privacy > Simplicity > Quality > Performance > Cost`):

- **Privacy** no se compromete: el `BearerAuthMiddleware` ya autentica cada request con bearer hash + scoping per-user en DB. Un actor que falsifique el `Host` aún necesita un bearer válido para acceder a datos.
- **Simplicity** gana significativamente: opción B requería mantener allowlist por CIDR por deploy, frágil cuando cambian las redes privadas; opción A bloqueaba el deployment.
- El threat model "DNS rebinding desde browser local" no aplica al deployment self-hosted en rig sin browser.

## Consecuencias

**Positivas**:

- Cualquier cliente con bearer válido puede conectar al MCP server independientemente del CIDR de la red privada (ZeroTier, LAN, Tailscale futura).
- Cero mantenimiento de allowlists por deploy.

**Negativas**:

- Si en el futuro se expone el MCP server a internet (NO recomendado por privacy), DNS rebinding desde un browser comprometido podría usar el server como pivot interno. Mitigación: reactivar la protección en ese deployment.
- Un misconfig del firewall del rig (puerto `8000` abierto a internet) deja la API accesible solo con bearer auth, sin la defensa adicional del Host check.

**Neutras**:

- La protección se reactiva cambiando `enable_dns_rebinding_protection=True` y proveyendo `allowed_hosts` específicos. Decisión reversible por config sin cambio de código.

## Cuándo revisitar

Esta decisión asume deployment intranet-only. Revisitar si:

1. Se planea exponer el MCP server a internet (cambio de modelo de amenaza).
2. Se introduce un browser legítimo en el rig que pueda visitar páginas externas (vector DNS rebinding pasa a aplicar).
3. El SDK Anthropic agrega una nueva clase de protección en `TransportSecuritySettings` que sea low-cost y compatible con CIDRs privados; reactivar si aplica.
