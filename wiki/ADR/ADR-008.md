# ADR-008: PostgreSQL para datos persistentes (reemplaza ADR-004 parcialmente)

## Estado

Aceptada
Reemplaza parcialmente: ADR-004

Fecha: 2026-04-30

## Contexto

ADR-004 estableció filesystem local sin BD para el caché efímero de 24 horas. Esa decisión sigue siendo correcta para su caso de uso. Sin embargo, el alcance del proyecto se amplió tras decisiones del PO (2026-04-30) para incluir multi-tenancy con login Microsoft SSO, histórico persistente de transcripciones por usuario, gestión de imágenes asociadas, y tokens OAuth para autorización del MCP server. Estos datos requieren queries cruzadas (todas las transcripciones de un user, búsqueda por texto, filtrado por rango de fechas), transaccionalidad (escritura atómica de user + token al login), y schema evolutionable (campos nuevos sin recomputar archivos JSON sueltos). Filesystem JSON puro no escala a estas necesidades.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: PostgreSQL 16 | DB relacional con JSON columns para metadatos flexibles | Production-grade, transacciones ACID, queries SQL, JSONB para schemas evolucionables, replicación si crece | Otro container en docker-compose; backup operativo (pg_dump) |
| B: SQLite | Un archivo `data/app.db` sin servicio adicional | Sin infra extra; aligned con Simplicidad | Concurrencia limitada (writers serializados); queries menos ricas; menos features |
| C: Filesystem JSON puro | Mantener ADR-004 al 100 % | Cero infra | Queries cruzadas dolorosas; sin transacciones; schema implícito |
| D: MongoDB | NoSQL document store | Schema flexible | Otra tecnología nueva al stack; sin SQL real |

## Decisión

Se elige **Opción A (PostgreSQL 16)**. Anclado en Calidad (prioridad #3) y respeto a Privacy (prioridad #1): la robustez transaccional para users + tokens es crítica para autenticación segura. JSONB columns absorben metadatos flexibles sin migraciones costosas.

**División clara entre PostgreSQL y filesystem**:

| Datos | Storage | Justificación |
|---|---|---|
| Users (id, email, microsoft_oid, created_at) | Postgres | Identidades de larga vida; queries por email/oid |
| OAuth tokens (encrypted) | Postgres | Vinculados a user, transaccionales con login |
| Transcripciones histórico (id, user_id, audio_hash, language, duration, text, segments_json) | Postgres | Queries por user, search en text, paginación |
| Images (id, transcription_id, filename, caption) | Postgres (metadatos) + filesystem (blobs) | Metadatos transaccionales; binarios en disco |
| Caché efímero por audio_hash (RF-TRX-02) | Filesystem | Sigue ADR-004 |
| Modelos pre-descargados (Whisper, pyannote) | Filesystem | Volumen Docker, no aplica DB |
| Audio temporal post-upload | Filesystem | Borrado en `finally` del request |

ADR-004 se mantiene vigente solo para el caché efímero indexado por SHA-256 del audio normalizado (idempotencia del pipeline). Toda dato persistente con identidad de usuario va a Postgres.

## Consecuencias

**Positivas**:
- Queries `SELECT * FROM transcriptions WHERE user_id = ? ORDER BY created_at DESC LIMIT 50` son baratas e idiomáticas.
- Search full-text vía `tsvector` sobre el campo `text` (búsqueda en transcripciones).
- Transacciones ACID para escenarios crítticos (login + token storage atómico).
- JSONB para metadatos del pipeline sin migration por cada cambio de schema.
- Backup/restore estándar con `pg_dump`; recuperación familiar para admins.

**Negativas**:
- Otro container en docker-compose, mitigable con healthcheck y volumen persistente.
- Operador del rig debe entender backups básicos de Postgres.
- Mitigación: documentar comandos `pg_dump`/`pg_restore` en `docs/DEPLOYMENT.md` cuando se cree.

**Neutras**:
- Impacto en arquitectura: agregar componente "Persistencia Relacional" en §3 de arquitectura, agregar sección "Persistencia" en §6.
- No invalida ADR-004 — convive como caché de pipeline, separado del histórico persistente.
