# ADR-011: MCP Server como protocolo principal + REST mínimo para blobs

## Estado

Aceptada

Fecha: 2026-04-30

## Contexto

Las decisiones del PO del 2026-04-30 establecen que la integración primaria con el sistema es a través del cliente Claude del usuario (Claude Code o Claude Desktop). Estos clientes son consumidores nativos de servidores Model Context Protocol (MCP). MCP fue diseñado para tools, resources y prompts — todos intercambiados como JSON. No fue diseñado para transferencia binaria grande: codificar un MP4 de 500 MB en base64 produce ~700 MB de tokens, lo que es prohibitivo en costo y latencia. El sistema necesita un canal eficiente para uploads binarios sin abandonar MCP-first como paradigma de interacción.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: REST API completa + MCP duplicando funciones | Dos APIs paralelas, ambas con todo | Flexibilidad máxima | Mantenimiento duplicado; superficie de testing 2x |
| B: Solo REST, sin MCP | Claude consume HTTP estándar | Familiar | Pierde discoverability MCP (resources, tools registradas); cliente Claude requiere prompt manual |
| C: MCP-first + HTTP mínimo solo para blobs | MCP es la superficie principal; HTTP solo para uploads binarios | Single source of truth; UX nativa de Claude | Requiere implementar MCP server custom |
| D: Solo MCP, blobs en base64 inline | Todo por MCP | Conceptualmente puro | Inviable: tokens explotan con archivos grandes |

## Decisión

Se elige **Opción C (MCP-first + HTTP mínimo para blobs)**. Alineado con Simplicidad (prioridad #2): single source of truth, REST con superficie minimal.

### Tools MCP (lifecycle completo)

| Tool | Propósito |
|---|---|
| `request_upload_url(file_type, file_size_bytes)` | Devuelve `{upload_url, upload_id, bearer_token, expires_at}` para subir blob |
| `start_transcription(upload_id, language?, max_speakers?, min_speakers?)` | Dispara pipeline asíncrono; devuelve `transcription_id` |
| `get_transcription(transcription_id)` | Devuelve el JSON completo (segments, words, speakers, metadata) |
| `list_my_transcriptions(limit?, offset?, sort?)` | Historial paginado del user |
| `search_my_transcriptions(query, limit?)` | Search full-text en el campo `text` (Postgres `tsvector`) |
| `request_image_upload_url(transcription_id)` | URL para subir imagen asociada |
| `attach_image(transcription_id, image_id, caption?)` | Asocia imagen previamente uploaded a una transcripción |
| `delete_transcription(transcription_id)` | Borra (soft delete) la transcripción |
| `get_user_info()` | Retorna info del user actual (name, email, oid) |

### Resources MCP (browseable)

| Resource URI | Contenido |
|---|---|
| `transcription://{id}` | JSON completo de una transcripción |
| `transcription://{id}/images/{image_id}` | Una imagen asociada (binario) |
| `user://me/transcriptions` | Lista paginada (proxy a `list_my_transcriptions`) |

### Endpoints REST (mínimos)

| Endpoint | Propósito |
|---|---|
| `POST /api/upload` | Recibe blob de audio (multipart), bearer auth, devuelve `upload_id` |
| `POST /api/upload-image` | Recibe blob de imagen (multipart), bearer auth, devuelve `image_id` |
| `GET /api/health` | Liveness check (sin auth) |
| `GET /auth/login` | Inicia flow OAuth Microsoft (browser) |
| `GET /auth/callback` | Callback OAuth, setea cookie de sesión |
| `POST /auth/logout` | Cierra sesión web |
| `POST /auth/regenerate-mcp-token` | Genera nuevo bearer para el MCP del user |
| `GET /` | Sirve UI React (StaticFiles) |
| `GET /mcp` | MCP server endpoint (streamable HTTP transport) |

### Transport y autenticación MCP

- **Transport**: streamable HTTP (no stdio, porque el server vive remoto en el rig).
- **Auth**: OAuth 2.1 Bearer token. El user obtiene su bearer en la UI tras login (ADR-009). El bearer está vinculado a su `user_id` en Postgres y a su token de Entra.
- **Per-user scoping**: cada tool y resource opera bajo la identidad del bearer; un user nunca ve transcripts de otro.

### Flujo concreto end-to-end (Claude Code)

```
User: "transcribí /Users/franco/reunion.mp4"

Claude Code:
  1. Bash: stat /Users/franco/reunion.mp4 → file_size=487MB
  2. MCP tool: request_upload_url(file_type="audio/mp4", file_size_bytes=487654321)
     ← {upload_url: ".../api/upload?token=...", upload_id: "u_abc123", bearer: "...", expires_at: "..."}
  3. Bash: curl -F file=@/Users/franco/reunion.mp4 -H "Authorization: Bearer <bearer>" <upload_url>
     ← {ok: true, upload_id: "u_abc123"}
  4. MCP tool: start_transcription(upload_id="u_abc123", language="es", max_speakers=4)
     ← {transcription_id: "t_xyz789", status: "processing"}
  5. (opcionalmente espera o usa long-polling MCP)
  6. MCP tool: get_transcription(transcription_id="t_xyz789")
     ← {duration_seconds: 3247.5, language: "es", num_speakers: 3, segments: [...], ...}
  7. Claude usa el JSON para generar la minuta en contexto del user
```

## Consecuencias

**Positivas**:
- Single source of truth: el MCP server expone toda la lógica de negocio.
- REST minimal-surface (3 endpoints reales + auth): menos código, menos tests.
- Claude Code y Desktop tienen UX nativa: tools y resources discoverables, sin documentación adicional.
- `Resources` browseables permiten que Claude navegue transcripciones sin que el user las nombre.

**Negativas**:
- No hay aún (al momento de escribir el ADR) una librería Python "completa" para MCP server con OAuth integrado; se va a usar el SDK oficial `mcp` de Anthropic más glue code.
- Mitigación: el SDK cubre transport + tools + resources; OAuth se integra con `authlib` o middleware custom de FastAPI.
- Tests E2E del MCP server requieren un cliente MCP de prueba.
- Mitigación: usar el cliente del SDK `mcp` en pytest fixtures; validar tools y resources programáticamente.

**Neutras**:
- Documentación al user en `/mcp-setup` debe explicar las dos configs (Claude Code: `.mcp.json` en proyecto; Claude Desktop: `claude_desktop_config.json`).
- El bearer token tiene rotación manual por ahora (botón "regenerar" en la UI). Política de expiración automática se difiere.
