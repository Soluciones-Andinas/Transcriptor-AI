# ADR-015: Listener de scoping fail-closed (reemplaza ADR-014)

## Estado

Aceptada — **Reemplaza [ADR-014](ADR-014.md)**.

Fecha: 2026-05-05

## Contexto

[ADR-014](ADR-014.md) introdujo un listener de `do_orm_execute` que inyecta `WHERE user_id = X` cuando `session.info["user_id"]` está armado, y queda como **no-op** cuando el flag no está seteado (caso "admin / migration / tests sin scoping").

El review multi-agente sin context-poisoning sobre el código de Capa 2 (auth Microsoft Entra + middleware MCP, 2026-05-05) identificó este comportamiento por defecto como un riesgo estructural de privacidad: si en alguna ruta futura (Capa 3+ pipeline endpoints, Capa 4 MCP tools, Capa 6 resources) se omite por error la dependencia `Depends(get_current_user_*)` que arma el `user_id`, una query naive contra un per-user model retorna **todas las filas de todos los usuarios** sin emitir un solo warning. El listener no actúa como guard, actúa como amplificador silencioso del bug.

Esto es exactamente la clase de bug que la prioridad #1 del proyecto (Privacy) busca eliminar: un olvido en un único call-site colapsa el aislamiento entre tenants.

La auditoría también notó que el bypass intencional, vía mutación inline `session.info["scoping_bypass"] = True`, era frágil:

- No exception-safe: si la query bajo bypass raise, el flag queda seteado en la sesión.
- Difícil de auditar: el grep encuentra los flips pero el match `pop` necesario debe estar en el `finally` correspondiente — fácil de olvidar.
- No declarativo: el call-site no comunica claramente "esta operación es legítimamente cross-user".

## Decisión

**Listener fail-closed por defecto** + **`bypass_scoping(session)` como context manager**.

### Cambio de contrato del listener

Una query SELECT/UPDATE/DELETE contra un per-user model (mappers que carrían columna `user_id`) sobre una sesión que **no tiene** `session.info["user_id"]` armado **ni** `session.info["scoping_bypass"] = True` debe **raise `ScopingNotArmedError`** (subclase de `RuntimeError`), no retornar todas las filas.

Implementación en `src/transcription_api/db/scoping.py`:

```python
class ScopingNotArmedError(RuntimeError):
    """Per-user model query attempted on an un-armed session."""

def _on_orm_execute(state):
    if not (state.is_select or state.is_update or state.is_delete):
        return
    if _scoping_bypass(state):
        return
    mapper = state.bind_mapper
    if mapper is None or mapper.class_ not in _scoped_models():
        return  # not per-user model
    user_id = _resolve_user_id(state)
    if user_id is None:
        raise ScopingNotArmedError(
            f"Query against per-user model {mapper.class_.__name__} on a "
            "session that has neither session.info['user_id'] (production "
            "scoping) nor session.info['scoping_bypass']=True (auth lookup / "
            "admin)."
        )
    state.statement = state.statement.where(mapper.class_.user_id == user_id)
```

### Cambio del API de bypass

Reemplazar las mutaciones inline por un context manager:

```python
@contextmanager
def bypass_scoping(session):
    prior = session.info.get("scoping_bypass")
    session.info["scoping_bypass"] = True
    try:
        yield
    finally:
        if prior is None:
            session.info.pop("scoping_bypass", None)
        else:
            session.info["scoping_bypass"] = prior
```

Call-sites legítimos (auth lookups + admin):

```python
with bypass_scoping(session):
    user = (await session.execute(
        select(User).where(User.microsoft_oid == oid)
    )).scalar_one_or_none()
```

## Justificación

Privacy > Simplicity > … (orden global del proyecto).

| Aspecto | ADR-014 (fail-open) | ADR-015 (fail-closed) |
|---|---|---|
| Olvido de `Depends(get_current_user_*)` | Leak silencioso de TODAS las filas | `RuntimeError` 500 inmediato visible en tests + producción |
| Auditoría de cross-user ops | Buscar `session.info["scoping_bypass"]` en grep | Buscar `bypass_scoping(` en grep — más expresivo, más fácil filtrar falsos positivos |
| Exception safety en bypass | Manual `try/finally` con `pop`, fácil de olvidar | Context manager garantiza el restore en el `finally` interno |
| Costo en código existente | — | Auth lookups + factories de tests + admin queries deben envolverse en `bypass_scoping(...)`. Trabajo acotado: 4 sitios en producción + 1 fixture global de tests |

El cambio convierte un bug-class entera ("forgotten auth dependency") de silencioso (leak masivo) en ruidoso (500 inmediato). En un servicio donde la prioridad #1 es Privacy, ese trade es siempre favorable.

## Impacto en código existente

Sitios actualizados al adoptar fail-closed (commit `d66f03b` y siguientes):

- `auth/dependencies.py::get_current_user_web` y `get_current_user_mcp`: el lookup del User por `id` o el lookup del bearer por hash van envueltos en `bypass_scoping(db)`.
- `auth/mcp_bearer.py::verify_bearer`: bypass durante el lookup del bearer.
- `auth/routes.py::callback`: el upsert completo del user va bajo `bypass_scoping`.
- `db/session.py::get_session`: cleanup en `finally` de `db.info["user_id"]` y `db.info["scoping_bypass"]` post-request (defensa en profundidad para refactors futuros que cacheen sesiones).
- `tests/conftest.py::session` fixture: arma `scoping_bypass = True` una vez por test (las factories y queries de verificación son admin-equivalent).
- `tests/integration/test_scoping_enforcement.py`: reescrito para el nuevo contrato. La autouse fixture pop el bypass del conftest para que los tests puedan observar el `RuntimeError` cuando corresponde.

Capa 3 en adelante: el orchestrator del pipeline corre bajo `bypass_scoping` durante la inserción del row de `transcriptions` (sería redundante el self-scoping al user del bearer, ya está armado por el dependency). Documentar el por qué en cada call site.

## Consecuencias

**Positivas**:

- La clase de bug "endpoint nuevo sin `Depends(get_current_user_*)`" ahora se manifiesta como 500 visible (no como leak silencioso). Tests integration con bearer válido + endpoint sin dependency → test fail inmediato.
- Bypass intencional declarativo: `with bypass_scoping(session): ...` documenta la intención cross-user en la línea de la operación.
- Exception-safe por construcción: cleanup del flag garantizado aunque el cuerpo del `with` raise.

**Negativas**:

- Tests de Capa 1 que asumían fail-open ("admin context = sees all rows") debieron reescribirse para usar `bypass_scoping` explícito o probar el raise.
- Un `bypass_scoping` mal puesto (envolviendo todo el handler "para que funcione") deshabilita la protección — code review debe inspeccionar el scope mínimo del bypass.

**Neutras**:

- El nombre `ScopingNotArmedError` es opinionado pero claro: distingue del `PermissionError` semántico (auth fail) y del `IntegrityError` (DB fail).

## Test de invariante

Reescritura de `tests/integration/test_scoping_enforcement.py`:

1. Setup: 2-3 users con rows propias (factories corren bajo `bypass_scoping`).
2. Sin scoping y sin bypass: query naive contra per-user model → `pytest.raises(ScopingNotArmedError)`.
3. Scope a user A: queries retornan solo rows de A.
4. Scope a user B: queries retornan solo rows de B.
5. `bypass_scoping(session)` permite ver cross-user para mantenimiento.
6. `users` table no se ve afectada por scoping (scope a user A retorna ambos users — el id IS el user, scopeo a sí mismo no aplica).
