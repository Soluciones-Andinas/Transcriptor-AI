# ADR-003: API síncrona sin queue ni callbacks

## Estado

Aceptada

Fecha: 2026-04-30

## Contexto

Una transcripción de 1 hora de audio tarda ~10-12 minutos en procesarse. Hay tres patrones de API posibles: síncrono (cliente espera la respuesta HTTP completa), asíncrono con polling (cliente sube → recibe job ID → consulta estado), asíncrono con webhook (cliente sube → recibe ack → recibe callback al terminar). El cliente (PO) explicitó: "no nos interesa hacer la llamada después, darle el ID y demás". Volumen esperado: ~20 reuniones/mes. Prioridad del proyecto: **Privacidad > Simplicidad > Calidad > Performance > Costo**.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Síncrono | El cliente espera la respuesta HTTP completa hasta que el pipeline termina | Simpleza máxima; sin estado persistente; sin Redis ni workers | Request HTTP largo; cliente debe configurar timeout adecuado |
| B: Async con polling | Cliente sube → recibe job ID → consulta `GET /jobs/{id}` cada N segundos | Cliente no bloquea conexión HTTP | Requiere persistir estado de jobs; complejidad de polling; agrega tabla/Redis |
| C: Async con webhook | Cliente sube → recibe ack → API hace POST a URL del cliente al terminar | Más eficiente que polling | Cliente debe exponer endpoint receptor (alta fricción en intranet); requiere queue |

## Decisión

Se elige **Opción A (síncrono)**. Alineado con Simplicidad (prioridad #2): elimina la necesidad de Redis, workers separados, persistencia de estado de jobs y lógica de polling/webhooks. El volumen esperado de 20 reuniones/mes ≈ 1 cada 2-3 días no justifica la complejidad operativa de un patrón asíncrono. El cliente puede ejecutar el upload en background con `curl &` o equivalente y revisar el JSON cuando termine.

## Consecuencias

**Positivas:**
- Stack reducido a FastAPI + Uvicorn; sin Redis, sin RabbitMQ, sin Celery.
- Sin estado persistente más allá del caché filesystem.
- Cliente trivial de implementar (un solo POST).

**Negativas:**
- Timeout HTTP debe ser configurado generosamente en cliente y servidor (recomendado 30 min).
- En caso de desconexión del cliente durante el procesamiento, el resultado se pierde (mitigación: el caché filesystem permite re-subir sin recomputar).
- Lock global de concurrencia (1 request por vez): ver ADR-005.

**Neutras:**
- Si en futuro el volumen sube a >5 reuniones/día, este ADR debe reemplazarse por uno asíncrono.
