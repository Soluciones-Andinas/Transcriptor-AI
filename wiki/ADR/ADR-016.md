# ADR-016: Defensa en capas para per-user scoping

## Estado

Aceptada — Hereda contexto de [ADR-015](ADR-015.md). **NO reemplaza** ADR-015; agrega una capa adicional de defensa.

Fecha: 2026-05-07

## Contexto

[ADR-015](ADR-015.md) estableció el listener `do_orm_execute` con comportamiento fail-closed contra modelos que carrían columna `user_id`. Una query naive sobre un per-user model con `session.info["user_id"]` no armado raisea `ScopingNotArmedError` en lugar de devolver todas las filas. Esto cierra el riesgo de un call-site que olvida `Depends(get_current_user_*)`.

El review multi-agente de Capa 4 (2026-05-06) identificó un fail-OPEN trap residual: el listener clasifica como per-user model a aquel mapper cuya tabla declara columna `user_id`. Un modelo nuevo introducido en Capa 5+ que represente datos del usuario pero **omita la columna `user_id`** queda fuera de `_scoped_models()` y por lo tanto fuera del enforcement del listener. Resultado: queries cross-user devuelven todas las filas silenciosamente, exactamente lo que ADR-015 intenta prevenir.

El review identificó tres ejemplos plausibles de regresión futura:

1. Una entidad `Bookmark` que olvide `user_id` y use sólo `transcription_id` como FK (asumiendo "ya está scopeada por la transcripción").
2. Una vista materializada que agregue stats per-user sin la columna explícita.
3. Una tabla auditoría `AuditLog` con `actor_id` en lugar de `user_id` por inconsistencia de naming.

En los tres casos el listener no actúa, no emite warning, y el modelo se carga durante migrations sin que ningún test de Capa 4 lo detecte.

## Decisión

Defensa en dos capas. Ambas deben coincidir o el servicio rehúsa arrancar.

### Capa 1 — Runtime listener (ADR-015 vigente)

El listener `do_orm_execute` registrado en `enable_per_user_scoping()` inyecta `WHERE user_id = X` en cada query SELECT / UPDATE / DELETE contra modelos de `_scoped_models()`. Sin cambios respecto a ADR-015.

### Capa 2 — Startup classification guard

`db/scoping.py::_validate_model_classification(mappers)` corre durante el lifespan de FastAPI y para cada mapper en `Base.registry.mappers` exige que la clase ORM esté en una de dos categorías declarativas:

- Carry `user_id`: el listener la enrola automáticamente vía `_scoped_models()`.
- Listada en `_NON_SCOPED_MODELS = frozenset({"User"})`: explícitamente exenta porque IS la entidad raíz per-user.

Cualquier mapper que no caiga en ninguna categoría dispara `ScopingClassificationError` durante el startup. El servicio falla loud (no arranca) en lugar de servir requests con un modelo no clasificado.

```python
# Pseudocódigo del guard (Capa 4):
def _validate_model_classification(mappers):
    for mapper in mappers:
        cls = mapper.class_
        has_user_id = hasattr(cls, "user_id")
        is_root = cls.__name__ in _NON_SCOPED_MODELS
        if not (has_user_id or is_root):
            raise ScopingClassificationError(
                f"{cls.__name__} carece de user_id y no está en _NON_SCOPED_MODELS"
            )
```

## Consecuencias

- Cualquier modelo nuevo en Capa 5+ que olvide `user_id` y no esté allowlisted ROMPE startup con `ScopingClassificationError`. Loud failure, no silent leak.
- Tests existentes siguen verde porque la clasificación actual es limpia (todos los per-user models declaran `user_id`; sólo `User` está en `_NON_SCOPED_MODELS`).
- Para agregar un modelo realmente global (`Config`, `AuditLog` global, feature flags) la operación es:
  1. Crear el modelo sin `user_id`.
  2. Documentar en el commit por qué es global.
  3. Update `_NON_SCOPED_MODELS` con el nombre de la clase.
  4. Code review explícito sobre Privacy implications.

  Esa fricción adicional es deliberada: el camino "fácil" (agregar el modelo) rompe startup; el camino correcto exige un review humano.
- El guard corre al boot, no por request. Cero overhead en hot path.
- Los tests de la suite `tests/unit/db/test_scoping_classification.py` cubren el guard: positivo (clasificación limpia hoy) y negativo (un mock mapper sin `user_id` ni allowlist dispara el error).
