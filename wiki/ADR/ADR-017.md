# ADR-017: Upload de blobs con bearer efímero per-upload (S3-style)

## Estado

Aceptada — Reemplaza a [ADR-013](ADR-013.md)

Fecha: 2026-05-11

## Contexto

[ADR-013](ADR-013.md) (2026-04-30) eligió la Opción A para upload de blobs: `POST /api/upload` autenticado con el bearer MCP del cliente. La justificación fue Simplicidad: "reutiliza el bearer ya gestionado por OAuth; no se reintroduce un sistema de auth paralelo".

Durante la implementación de Capa 4 (2026-05-06) el equipo se desvió silenciosamente a la Opción B de ADR-013 (signed URLs temporales) sin reemplazar el ADR. La desviación se detectó en el audit multi-agente del 2026-05-11 (drift **D-050**, `docs/sesiones/2026-05-11-wiki-drift-audit.md`).

La razón del refactor durante la implementación fue una restricción de Privacy no anticipada en ADR-013:

- El bearer MCP es **de larga duración**: válido hasta que el usuario llame `/auth/regenerate-mcp-token` (puede ser meses).
- Si un proxy o nginx intermedio loguea el header `Authorization` (default en muchas configs de access log), el bearer MCP queda comprometido **indefinidamente**.
- ADR-013 mencionaba esto como riesgo y proponía mitigarlo "configurando logging para redactar el header `Authorization`". En la práctica, la garantía es frágil: depende de cada proxy en el path (ZeroTier no aplica, pero un nginx futuro frente al rig sí), y un misconfig deja el secret indefinido en disco.

El patrón estándar de la industria para uploads de blobs grandes con identidad del cliente (AWS S3 presigned URLs, Google Cloud Storage resumable uploads, Azure Blob SAS tokens) usa la Opción B precisamente por esta razón.

## Opciones Consideradas (re-evaluación)

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Bearer MCP en `/api/upload` (ADR-013) | Cliente envía `Authorization: Bearer <bearer_MCP>`; mismo `BearerAuthMiddleware` valida | Sistema de auth único; sin estado intermedio | Bearer indefinido leakable en access logs; blast radius enorme si compromete |
| **B: Bearer efímero per-upload (S3-style)** | `request_upload_url` emite un secreto efímero hasheado en `upload_sessions.upload_bearer_hash`; `/api/upload` valida hash con `hmac.compare_digest` | Blast radius ~10 min; estándar industria; sin riesgo de leak indefinido | Una columna DB extra (`upload_bearer_hash`) + 1 sistema de auth adicional |
| C: Híbrido (ambos bearers aceptados) | `/api/upload` acepta cualquiera | Migración gradual posible | Doble superficie de testing; el riesgo de A se mantiene si clientes lo siguen usando |

## Decisión

Se elige **Opción B (bearer efímero per-upload)**, formalizando el patrón ya implementado en Capa 4.

**Patrón concreto** (as-built en `src/transcription_api/api/upload.py` y `src/transcription_api/mcp/tools/upload.py`):

1. Cliente llama tool MCP `request_upload_url(kind, file_size_bytes, mime_type?, transcription_id?)` autenticándose con su bearer MCP normal.
2. El MCP server:
   - Genera un secreto plaintext con `secrets.token_urlsafe(48)` (~64 chars URL-safe).
   - Hashea con `sha256` y lo guarda en `upload_sessions.upload_bearer_hash`.
   - Inserta una row con `status='requested'`, `expires_at = now() + 10 min`, `user_id`, `expected_mime_type`, `expected_size_bytes`, `transcription_id` (si aplica).
   - Devuelve `{upload_url: "/api/upload?session=<upload_id>", upload_token: <plaintext>, expires_at}`.
3. Cliente hace `POST /api/upload` con `Authorization: Bearer <plaintext>` y el binary.
4. El endpoint:
   - Carga la row `upload_sessions` por `upload_id`.
   - Valida `expires_at + grace_seconds > now()` (grace ≈ 30s para absorber clock skew).
   - Valida `status == 'requested'` (single-use).
   - Hashea el bearer recibido y compara con `upload_bearer_hash` vía `hmac.compare_digest` (constant-time).
   - Si OK: persiste el binario en `<DATA_DIR>/uploads/<upload_id>/original.bin`, marca `status='uploaded'`, devuelve `200`.
   - Si falla por cualquier razón (bearer mismatch, expirado, ya consumido, mime mismatch, tamaño excedido): devuelve `401` o `403` con `error_code` específico, **sin distinguir entre "row inexistente" y "bearer inválido"** (AC-10: no-existence-leak).

**Por qué B y no A en 2026-05-11**:

- **Privacy** (prioridad #1 del proyecto, ver CLAUDE.md §4): blast radius del bearer efímero es ≤10 min; el del bearer MCP era indefinido. Bajo cualquier modelo de amenaza con logs persistidos en proxies, B reduce el riesgo en órdenes de magnitud.
- **Simplicity** (prioridad #2): el costo de B es 1 columna DB + ~50 LOC de validación + 1 set de tests. Comparado contra el riesgo de Privacy, es una inversión barata.
- **Industria**: S3 / GCS / Azure Blob convergieron en este patrón por la misma razón. No es over-engineering, es la solución estándar al problema.

**Aplica a imágenes**: el mismo patrón con `kind="image"` en `request_upload_url` (no hay tool separada `request_image_upload_url`; ver drift D-043 y D-075 del audit). La unificación bajo un solo tool con discriminador `kind` ocurrió en Capa 4.

## Consecuencias

**Positivas**:

- Bearer leak en access logs tiene impacto temporal acotado a 10 min.
- Patrón alineado con la industria; reviewers externos lo reconocen sin contexto adicional.
- Schema `upload_sessions.upload_bearer_hash` ya existe (migration `1a4f8c9b2d6e_add_upload_bearer_hash.py`); el ADR formaliza algo ya productivo.
- `BearerAuthMiddleware` del MCP queda limpio: solo valida bearers MCP, no carga lógica de upload.

**Negativas**:

- Dos sistemas de auth conviven: bearer MCP (long-lived, para tool calls MCP) y bearer efímero (10-min TTL, solo para `/api/upload` y `/api/upload-image`). Documentar en cada endpoint qué tipo espera.
- Un cliente confundido podría intentar usar el bearer MCP en `/api/upload`: el endpoint debe responder 401 claro con un mensaje accionable (current behavior: error genérico, podría mejorarse en futuras iteraciones).

**Neutras**:

- Si en futuro se externaliza el storage a S3/MinIO, el patrón se generaliza naturalmente: el `upload_url` deja de apuntar a `/api/upload` y empieza a apuntar a la signed URL de S3. El contrato con el cliente no cambia.
- El grace_seconds para clock skew quedó accidentalmente en 300s en lugar de 30s (D-051 del audit del 2026-05-11). Se corrige por separado; no afecta esta decisión.
