# ADR-012: Generación de minutas en Claude del usuario, no en backend

## Estado

Aceptada

Fecha: 2026-04-30

## Contexto

La motivación del proyecto (sección §1 de `01_alcance_funcional.md`) es "captura de requerimientos sin que se escape detalle". Una primera lectura sugería que el backend debía generar la minuta automáticamente como parte del pipeline. Tras las decisiones del PO del 2026-04-30 que incorporan integración con Claude vía MCP, se reevalúa: ¿la minuta la genera el backend (haciendo una llamada a un LLM externo o local) o la genera Claude del usuario consumiendo el transcript+imágenes vía MCP?

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Backend genera minutas (Claude API o LLM local) | Pipeline incluye paso final que llama a un LLM y produce minuta como parte del response | Cliente recibe todo en un único request | Requiere API key gestionada centralmente; costo recurrente facturado a Sandinas; vendor lock-in |
| B: Claude del user genera minutas con MCP | Backend solo entrega transcript + imágenes vía tools MCP; la generación pasa en el contexto del Claude del user | Cero costo recurrente para el backend; cada user usa su Claude (Desktop/Code) ya pago; el user puede iterar y refinar | El user debe tener Claude (no es problema en este equipo, ya lo usan) |
| C: Híbrido: backend genera draft + Claude refina | Backend produce minuta inicial, user la refina en Claude | Punto de partida para users sin Claude | Doble costo (backend + Claude); complejidad alta |

## Decisión

Se elige **Opción B (Claude del user genera minutas vía MCP)**. Anclado en Privacy (prioridad #1) y Costo (prioridad #5):

1. **Privacy**: el transcript sale de la intranet solo cuando el user pide explícitamente a su Claude que use el MCP. No hay envío automático ni implícito a un LLM cloud. El user controla cada vez.
2. **Costo**: el backend no paga tokens de LLM. Claude del user ya está pago como herramienta de trabajo de Sandinas. La minuta se genera dentro del plan del user.
3. **Flexibilidad**: el user puede pedirle a Claude "una minuta más corta", "incluí los nombres de quien dijo cada cosa", "agregá un párrafo de riesgos" sin tocar el backend.
4. **Sin vendor lock-in del backend**: el backend no depende de la API de ningún LLM particular. Si Anthropic cambia precios, el impacto es del user, no del proyecto.

**Excepción negociable**: si en el futuro se necesita generar minutas para usuarios que no tienen Claude (visitas, contractors), se puede agregar un endpoint backend que llame a Claude API u OpenAI. Eso requiere un nuevo ADR que justifique la regresión de Privacy y agregue manejo de API keys.

## Consecuencias

**Positivas**:
- Cero API key de LLM en el backend; sin facturación de tokens; sin gestión de rate limits.
- Cada user usa su Claude preferido (Code o Desktop) y su plan personal.
- Iteraciones de minuta son baratas y rápidas (el user le pide a Claude variantes).
- El backend mantiene su propósito: transcribir + diarizar + persistir + servir.

**Negativas**:
- El user debe tener Claude. Mitigación: el equipo de Sandinas ya usa Claude (`CLAUDE.md` global del repo lo confirma).
- Si el user no quiere Claude, puede recibir el transcript JSON y pegarlo manualmente en cualquier LLM. Solución degradada pero válida.

**Neutras**:
- La calidad de la minuta depende del prompt del user y del modelo Claude que use. No es responsabilidad del backend.
- El proyecto puede ofrecer "prompts sugeridos" (ej: "minuta de captura de requerimientos siguiendo SDD") como documentación, no como código.
