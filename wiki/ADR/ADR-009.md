# ADR-009: Microsoft Entra ID OAuth 2.0 / OIDC para autenticación

## Estado

Aceptada

Fecha: 2026-04-30

## Contexto

El alcance original (sección §6 de `01_alcance_funcional.md`) listaba "Autenticación / multi-tenancy" como fuera de alcance porque la red era intranet privada. Las decisiones del PO del 2026-04-30 mueven multi-tenancy y UI con login a dentro de alcance: cada usuario tiene su propia cuenta, su propio histórico de transcripciones, y su propia conexión Claude vía MCP autorizada por su identidad. Sandinas opera con Microsoft Suite (CLAUDE.md global del repositorio AdopcionIA lo confirma: Teams, Microsoft 365). Existe un tenant Microsoft Entra ID activo con identidades corporativas. Reusar esa identidad evita gestionar passwords adicionales.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Microsoft Entra ID OAuth 2.0 / OIDC | SSO contra el tenant corporativo de Sandinas | Cero gestión de passwords; aprovecha identidades existentes; OIDC es estándar; filtrado automático a personal de Sandinas | Requiere registro de app en Azure Portal; dependencia operativa con tenant Sandinas |
| B: Username + password local | Tabla `users` con bcrypt | Independiente | Gestión de passwords (rotación, recovery, compromiso); contradice integración con Suite ya en uso |
| C: Magic link via SMTP | Email-only auth | Sin passwords | Requiere SMTP server o servicio externo (SendGrid, etc.); fricción del email check |
| D: SAML | Federación enterprise | Compatible con muchos IdPs | Más complejo que OIDC para el mismo resultado |

## Decisión

Se elige **Opción A (Microsoft Entra ID OAuth 2.0 / OIDC)**. Alineado con Simplicidad (prioridad #2) y Privacy (prioridad #1): la identidad ya existe, el filtrado al dominio de Sandinas es automático (solo usuarios del tenant pueden loguearse), y no se introducen credenciales paralelas.

**Configuración propuesta**:
- Registro de app en Azure Portal del tenant Sandinas con `redirect_uri = https://<rig>:8000/auth/callback`.
- Scopes solicitados: `openid`, `profile`, `email`, `User.Read`.
- Flujo: Authorization Code con PKCE.
- Librería en backend: `authlib` o `msal` (Python).
- Persistencia de sesión: cookie HttpOnly + Secure con JWT firmado del backend (separado del token de Entra para no exponer el access_token).
- El `oid` (object id) de Entra es la clave de usuario en `users.microsoft_oid`.

**Doble uso del OAuth**:
1. Login en la UI del backend (web flow estándar).
2. Autorización del MCP server: el bearer token que Claude usa para hablar con el MCP server se obtiene del mismo flow OAuth, vinculando la identidad del user con sus tools MCP.

## Consecuencias

**Positivas**:
- Cero passwords gestionados por el backend.
- Onboarding instantáneo: cualquier empleado de Sandinas con cuenta corporativa puede entrar.
- Auditing: cada acción queda asociada al `oid` de Entra, trazable contra logs corporativos.
- Off-boarding automático: si IT desactiva la cuenta de un empleado en Entra, pierde acceso.

**Negativas**:
- Dependencia operativa del tenant Sandinas para login. Si el tenant tiene outage, los users no pueden loguearse durante la duración del outage. Mitigación: aceptable para uso interno; el rig sigue procesando trabajos en curso.
- Requiere coordinación con IT/Administración de Sandinas para registrar la app y conceder permisos de read básico.
- Mitigación: documentar el setup en `docs/DEPLOYMENT.md` con screenshots del Azure Portal.

**Neutras**:
- La cookie de sesión vive en el dominio del backend; reduce CSRF si se configura `SameSite=Strict` para cross-origin.
- El plan no contempla MFA específico — se hereda de la política del tenant Sandinas.
