# ADR-013: Upload de blobs (audio + imágenes) vía endpoints HTTP autenticados

## Estado

Reemplazada por [ADR-017](ADR-017.md)

Fecha: 2026-04-30
Reemplazada: 2026-05-11

> **Nota (2026-05-11)**: este ADR eligió la Opción A (bearer MCP en `/api/upload`). Durante la implementación de Capa 4, el equipo se desvió a la Opción B (bearer efímero per-upload, S3-style) por razones de Privacy no anticipadas al escribir este ADR — el bearer MCP indefinido leakable en access logs era un blast-radius inaceptable. [ADR-017](ADR-017.md) formaliza el patrón realmente implementado. Este documento queda como contexto histórico de la decisión original. Drift detection: `docs/sesiones/2026-05-11-wiki-drift-audit.md` D-050.

## Contexto

El flujo principal (Q2 cerrada como opción A en 2026-04-30) es: el usuario le pasa un archivo de audio (MP4/MP3/WAV) a su Claude Code o Claude Desktop, y este lo procesa vía el MCP server del backend. ADR-011 estableció que MCP no transporta blobs grandes eficientemente; necesitamos un canal HTTP separado. Este ADR define el patrón concreto de upload: cómo Claude transfiere el archivo del filesystem del usuario al backend, con qué autenticación, y cómo se vincula el upload con la posterior tool call de transcripción.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Endpoint HTTP autenticado con bearer del MCP OAuth | `POST /api/upload` con `Authorization: Bearer <token>` | Patrón estándar; un solo endpoint para todos los blobs; mismo bearer que MCP | Bearer del user en HTTP header (manejar con cuidado en logs) |
| B: Signed URLs temporales | El MCP server genera URL única por upload con token embebido | Token efímero; URL imposible de adivinar; permite mover el storage a S3-like sin cambiar protocolo | Más complejidad: gestionar tokens de upload en Postgres |
| C: Direct-to-object-storage signed URLs | El backend devuelve signed URL contra S3/MinIO/etc. | Backend no procesa el blob (escala) | Requiere object storage externo; no aplica self-hosted en intranet por ahora |
| D: Base64 inline en MCP tool call | Sin canal HTTP separado | Conceptualmente puro | Inviable: tokens explotan con archivos grandes (descartado en ADR-011) |

## Decisión

Se elige **Opción A (endpoint HTTP autenticado con bearer del MCP OAuth)** para la primera versión.

**Patrón concreto**:

1. El user le pasa un archivo a Claude (Code o Desktop): "transcribí este MP4".
2. Claude llama tool MCP `request_upload_url(file_type, file_size_bytes)`.
3. El MCP server responde con `{upload_url: "/api/upload?session=<sid>", upload_id, bearer_token, expires_at}`. El `session` es un nonce válido por 10 minutos para evitar replay.
4. Claude ejecuta su `Bash` tool: `curl -F file=@<path> -H "Authorization: Bearer <bearer_token>" <upload_url>`.
5. El endpoint `POST /api/upload`:
   - Valida el bearer (mismo OAuth Microsoft Entra del MCP).
   - Valida el `session` nonce.
   - Recibe el archivo, lo guarda en `/data/uploads/<upload_id>`.
   - Devuelve `{ok: true, upload_id}`.
6. Claude llama tool MCP `start_transcription(upload_id, language?, max_speakers?, ...)`.

**Por qué A y no B en primera versión**: A es estándar, fácil de testear con curl, y reutiliza el bearer ya gestionado por OAuth. B agrega complejidad de gestión de tokens efímeros sin ganancia visible cuando el storage es local. Cuando se considere escalar a object storage externo, este ADR se reemplaza por uno que use B o C.

**Aplica a imágenes también**: el mismo patrón con `request_image_upload_url()` y `attach_image()`.

**Compatibilidad por cliente Claude**:

| Cliente | Soporte |
|---|---|
| Claude Code | Soportado completo: usa `Bash` tool para `curl`, `Read` para path |
| Claude Desktop | Soportado parcial: el archivo adjunto al chat no es accesible directo desde una tool MCP; el user debe darle a Claude el path local, o subir vía la UI web (fallback documentado) |
| Claude.ai web (futuro) | Custom connectors soportan tools; el upload se haría con `fetch()` en el server-side del MCP |

## Consecuencias

**Positivas**:
- Patrón HTTP estándar, fácil de testear sin cliente MCP.
- Un solo endpoint sirve audio e imágenes (`/api/upload` y `/api/upload-image` con misma lógica).
- Bearer del OAuth ya valida la identidad; no se reintroduce un sistema de auth paralelo.

**Negativas**:
- Timeout HTTP requiere ajuste para archivos grandes. Mitigación: configurar uvicorn/nginx con timeout 30 min para `/api/upload`; el user puede dividir archivos muy largos manualmente.
- Si el bearer queda en logs (header `Authorization`), expone el token. Mitigación: configurar logging para redactar el header `Authorization` en `request_received`.
- En Claude Desktop el flujo "adjuntar archivo y que MCP lo transcriba" no funciona limpio; el user debe usar la UI web o tener el archivo en el filesystem (no en chat). Esto se documenta explícitamente.

**Neutras**:
- Si en futuro se externaliza el storage (S3/MinIO/Azure Blob), este ADR se reemplaza con uno que defina B o C. Hoy: simplicidad.
- El nonce `session` evita replay attacks pero no es obligatorio para correctness; es defensa en profundidad.
