# ADR-014: Per-user query scoping enforcement vía SQLAlchemy event listener

## Estado

Reemplazada — Reemplazada por [ADR-015](ADR-015.md) (2026-05-05).

Razón: el contrato fail-open ("listener no-op cuando `user_id` no está armado") fue auditado durante el review multi-agente de Capa 2 y catalogado como riesgo estructural de Privacy (CR-5). ADR-015 cambia el contrato a fail-closed (`ScopingNotArmedError` en lugar de no-op) y formaliza el bypass como context manager.

Fecha original: 2026-05-04
Fecha de reemplazo: 2026-05-05

## Contexto

A partir de Capa 6 (MCP server), el sistema corre queries arbitrarias por nombre del usuario autenticado contra todas las tablas que portan `user_id` (`oauth_tokens`, `mcp_bearers`, `transcriptions`, `images`, `upload_sessions`). Una sola query que olvide el `WHERE user_id = X` filtra datos de otros usuarios al user actual — un leak de datos sensibles entre tenants en una organización donde la privacidad ya está documentada como prioridad #1 (`02_arquitectura.md` §0).

La auditoría de review post-Capa 1 (sandinas-code-reviewer + code-architect, 2026-05-04) identificó este patrón como el riesgo estructural más alto pendiente. La FK CASCADE en cada tabla garantiza la integridad referencial, pero **no enforza el scoping en lectura**. "Disciplina del developer" en una codebase con MCP tools heterogéneas y ramas de feature paralelas no es suficiente.

Se necesita un mecanismo que:

1. Sea no-bypass por accidente: un `select(Transcription)` sin WHERE explícito debe igualmente quedar scoped al user activo.
2. Permita bypass intencional para jobs administrativos (cleanup, métricas cross-tenant) sin que el bypass sea silencioso.
3. No requiera cambiar la firma de cada query existente.
4. Sea verificable con un test de invariante que crece con la codebase.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Event listener `do_orm_execute` con WHERE injection | Listener global que inspecciona `state.bind_mapper`, agrega `cls.user_id == session.info["user_id"]` | Transparente; cubre SELECT/UPDATE/DELETE; opt-in via `session.info`; bypass explícito flag | Requiere atención al ciclo de cache de SQLAlchemy 2.x; no cubre raw SQL via `text()` |
| B: Repository pattern por entidad bound al user | `TranscriptionRepository(session, user_id)` con `where(user_id=self.user_id)` baked-in | Bulletproof; tipado fuerte | Refactor masivo; cada nueva tabla = nueva clase repository; abandona el ORM "natural" |
| C: `with_loader_criteria` con closure | API oficial de SQLAlchemy para inyectar criteria | Documentado | Bug observado en SQLAlchemy 2.0.49: el closure `_uid=user_id` queda baked en el cache key del statement compilado, todas las queries reusan el primer `user_id` (alice y bob ven datos de alice). Confirmado en debug 2026-05-04 — descartado |
| D: PostgreSQL Row-Level Security (RLS) | Policies a nivel DB con `SET app.current_user_id = X` | Defensa en profundidad real (incluso raw SQL queda scoped) | Complejidad operativa; requiere alinear roles Postgres con la app; debugging menos directo |

## Decisión

**A: SQLAlchemy `do_orm_execute` event listener con WHERE injection directa**.

Implementación en `src/transcription_api/db/scoping.py`:

- Listener registrado idempotentemente sobre `sqlalchemy.orm.Session` via `enable_per_user_scoping()`.
- Detecta `session.info["user_id"]`. Si no está seteado: no-op (admin / migration / tests sin scoping).
- Inspecciona `state.bind_mapper`. Si la entidad está en el set `{User-Aware}` (tabla con columna `user_id`), agrega `state.statement = state.statement.where(cls.user_id == user_id)`.
- Usa `state.statement.where()` directo en vez de `with_loader_criteria()` para evitar el bug de cache key descrito en opción C.
- Bypass intencional: `session.info["scoping_bypass"] = True` (también `state.execution_options["scoping_bypass"]`).
- Helper `set_session_user(session, user_id)` para Capa 2 middleware.

`users` queda excluida del scoping — el `id` es el user, scopeo a sí mismo no tiene sentido y rompería el lookup en login.

## Justificación

Privacy > Simplicity > … (orden global): el listener es la opción de menor cambio quirúrgico que provee la propiedad de privacidad correctamente.

- **A vs B**: A logra el mismo invariante con ~100 LOC vs B que requeriría ~6 clases repository + un patrón de inyección de dependencias para todos los handlers. Cuando llegue el día que necesitemos un Repository (e.g., agregaciones complejas, batch ops), se agrega encima de A sin conflictos.
- **A vs C**: rechazado por bug verificado en runtime (cache key reuse). Si en el futuro SQLAlchemy resuelve la limitación, se puede reemplazar A por C sin cambiar el contrato externo (`session.info["user_id"]` permanece estable).
- **A vs D**: RLS es la defensa más fuerte pero excede la complejidad operativa para v0.1. Mantener RLS como fallback futuro: si en algún momento se exponen vectores raw-SQL (e.g., un endpoint admin que hace queries arbitrarias), RLS pasa a ser obligatorio. Hoy: el ORM es la única superficie de query.

## Test de invariante

`tests/integration/test_scoping_enforcement.py` corre el patrón completo para los 5 modelos with-user-id:

1. Setup: 2 users (alice, bob) con rows propias en cada tabla.
2. Sin scoping (`set_session_user(s, None)`): la query ve ambos.
3. Scope a alice: solo rows de alice; **ninguna fila de bob**.
4. Scope a bob: solo rows de bob; **ninguna fila de alice** (cubre el bug C de cache).
5. `users` table no se ve afectada por el scoping (scope a alice retorna ambos users).
6. `scoping_bypass = True` permite ver cross-user para mantenimiento.

Cada nueva tabla con `user_id` queda automáticamente cubierta por la lógica del listener (lee `Base.registry.mappers` lazy-cached) y debe agregarse al parametrize de este test.

## Consecuencias

**Positivas**:

- Capa 6 puede tener developers escribiendo MCP tools sin recordar el WHERE explícito; el invariante es de la infra, no del autor.
- Bypass requiere acción explícita (`session.info["scoping_bypass"] = True`), que sale grep-friendly en code review como auditoría.
- El listener se aplica también a ORM UPDATE/DELETE: un `delete(Transcription).where(audio_hash == X)` ejecutado por bob no puede borrar el transcript de alice por accidente.

**Negativas**:

- Raw SQL via `text("SELECT ... FROM transcriptions ...")` no queda scopeado. Mitigación: en code review, banear raw SQL contra tablas with-user-id; usar `select(Transcription)` ORM-style. Si un caso justifica raw SQL, debe declarar explícitamente el scoping inline.
- Joins multi-tabla no scopean automáticamente todas las tablas (solo el `bind_mapper` primario). Mitigación: para joins de Capa 6, escribir queries que comiencen en la tabla user-aware más restrictiva, así el join hereda el filtro.
- Si el listener falla silenciosamente (raise dentro de `_on_orm_execute`), SQLAlchemy lo reporta pero la query puede caer al modo unsafe. Cobertura: el invariant test asserta cross-user isolation post-listener-load.

**Neutras**:

- Si en el futuro adoptamos Postgres RLS (opción D), este ADR se reemplaza. Por ahora es la herramienta correcta para la complejidad actual.
- La lista de modelos scoped se computa lazy desde `Base.registry.mappers`. Agregar una nueva tabla con `user_id` la incluye automáticamente; quitar `user_id` la excluye. No hay lista hardcoded que se pueda desincronizar.
