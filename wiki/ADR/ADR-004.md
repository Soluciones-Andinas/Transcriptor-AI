# ADR-004: Caché en filesystem local sin base de datos relacional

## Estado

Aceptada

Fecha: 2026-04-30

## Contexto

El sistema requiere persistencia temporal (24 horas) de las transcripciones para idempotencia: re-uploads del mismo audio dentro de la ventana deben devolver el resultado sin recomputar. El PO explicitó: "intentemos que no sea una base de datos relacional y demás nada complejo, que apunte directamente al filesystem de la computadora". Volumen esperado: ~20 reuniones/mes ≈ 0,67 transcripciones/día. Tamaño esperado de cada JSON de respuesta: 100 KB - 2 MB.

## Opciones Consideradas

| Opción | Descripción | Pros | Contras |
|---|---|---|---|
| A: Filesystem (directorios + JSON) | Un directorio por hash de audio con `transcription.json` y `meta.json` adentro | Cero dependencias; debug trivial (cat un archivo); backup con tar; alineado con pedido del PO | TTL implementado a mano; sin queries complejas |
| B: SQLite | Tabla con BLOB del JSON y timestamp | Queries SQL si se necesitan; transaccional; un solo archivo | Agrega dependencia (sqlite3); excede simplicidad pedida |
| C: Redis con TTL | Key-value store con expiración nativa | TTL automático; rapidísimo; estándar para caché | Requiere proceso adicional, configuración, memoria; viola Simplicidad |
| D: PostgreSQL / MySQL | DB relacional completa | Robusto, escalable | Excesivo para el volumen; viola pedido explícito del PO |

## Decisión

Se elige **Opción A (filesystem local)**. Alineado con Simplicidad (prioridad #2) y respuesta directa al pedido del PO. La estructura es:

```
<DATA_DIR>/cache/
└── <sha256-hash-del-audio-normalizado>/
    ├── transcription.json   # resultado completo
    └── meta.json            # { created_at, original_filename, duration, ttl }
```

Lookup: `os.path.exists(cache_dir / hash / "meta.json")` y verificar TTL en `meta.json`. Cleanup: barrido periódico que elimina directorios donde `now - created_at > TTL`.

## Consecuencias

**Positivas:**
- Cero infraestructura adicional (sin Redis, sin DB).
- Debug trivial: `ls cache/` y `cat <hash>/transcription.json`.
- Backup operativo con `tar -czf cache.tar.gz cache/`.
- El propio sistema operativo gestiona el storage; el límite es el disco del rig.

**Negativas:**
- TTL implementado en código (no nativo del storage). Mitigación: cleanup job en background task de FastAPI (ver ADR-005).
- No es atómico ante crashes a mitad de escritura (mitigación: escribir a `<hash>/.tmp.json` y rename al final).
- No es seguro ante concurrencia múltiple (mitigación: ADR-005 asegura 1 request a la vez).

**Neutras:**
- Tamaño del caché crece con uso. En 24 h con volumen pico de 5 reuniones/día y JSONs de 2 MB, ocupa ~10 MB. Monitoreable con simple `du -sh`.
